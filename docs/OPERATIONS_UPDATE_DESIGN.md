# 운영 업데이트 페이지 설계안

2026-10-28 **제안 단계**. 이미지 시안 확인 후 구현 예정이며 현재 통합 운영 API/페이지를 구현했다고 설명하지 않습니다. 기존 quick 동기화/토큰 수집기/분류기를 연결합니다.

## 화면

- 상단 OpenWebUI 데이터 / LiteLLM 토큰 / 질문 분류 카드: 마지막 성공 시각, 연결 상태, 현재 미처리 질문 수.
- 기본 버튼: 최근 변경분 업데이트. 실행 중 중복 실행 불가.
- 진행 타임라인: OpenWebUI 변경분 수집 → LiteLLM 토큰 수집 → 미처리 질문 자동 분류.
- 단계별 상태·시작/종료 시각·조회/신규/갱신/미반영 건수. 수집 총량을 모르는 동안 가짜 퍼센트 대신 진행 표시와 현재 조회 건수 사용.
- 분류는 시작 시점의 실제 대상 총건수를 알 수 있으므로 처리 건수/총건수와 진행률 제공. 분류 중지는 현재 모델 호출 결과 저장 후 종료.
- 최근 실행 내역: 종류, 단계별 결과, 안전한 오류 요약, 전체 성공/일부 실패/실패/중단. 새로고침 후에도 작업 상태 유지.
- 고급 작업: 전체 재대조, 전체 미처리 분류. 매번 full을 실행하는 기본 동작은 없음.
- 이미지의 숫자/날짜는 가상 예시. 화면 검수 후 라이트/다크와 작은 화면 대응.

## 실제 fetch 전략

| 단계 | 재사용할 구현 | 최근 변경분 판단과 보존 |
| --- | --- | --- |
| OpenWebUI | Synchronizer.run('quick') | 마지막 성공한 수집 **시작 시각**에서 overlap 기본7일을 뺀 구간. 사용자별 newest-first API 페이지를 읽고 경계에서 중단. 사용자 명부는 매번 전체 API로 확인하여 신규/삭제/조직 매핑을 반영. 새 사용자는 과거 이력도 최초 수집. 기존 사용자 전체 과거 메시지를 매번 수집하지 않음. |
| LiteLLM | token_sync quick | 독립적인 마지막 토큰 수집 성공 시작 시각에서 lookback 기본24시간을 뺀 구간. 첫 수집은 설정 시작일부터. 작은 날짜 구간/페이지로 읽고 request ID upsert. 키 별칭 필터 유지. |
| 카테고리 | category_sync pending | 현재 snapshot 중 결과 없는 해시만 자동 분류. 초기에는 전체 기간을 끝까지 처리, 이후에는 추가/수정된 질문만 처리. CSV/모델/프로필 변경 시 재분류 대상 증가를 명시. |

안전한 업데이트는 엄격하게 마지막 시각 이후만 읽는 방식과 다릅니다. 중복 구간을 조금 재조회해야 지연 도착·최근 수정/삭제를 반영할 수 있습니다. 중복은 메시지/request ID로 제거하고 성공 구간만 공개합니다. OpenWebUI 0.12.3 user_id 메시지 API는 날짜 인자를 실제 적용하지 않으므로 서버 시간 필터를 지원한다고 주장하지 않습니다. 조회는 최신 페이지부터 시작해 로컬에서 시간 경계를 검증합니다. overlap보다 오래된 변경/삭제는 정기 또는 수동 full 재대조가 필요합니다.

수집기별 마지막 성공 시각은 별도로 유지합니다. 부분 실패 때문에 토큰 시각을 OpenWebUI 시각으로 덮어쓰거나 반대로 덮어쓰지 않습니다. 최초 quick이 full로 승격되는 기존 동작과 명시적 최초 수집 시작일 요구는 유지합니다.

## 실행/실패 정책

1. 전역 운영 작업 잠금으로 중복 방지. 수집기별 기존 잠금도 유지하여 CLI나 별도 토큰/카테고리 버튼과 충돌하면 명시적으로 알림.
2. OpenWebUI quick 실패 시 뒤 단계는 실행하지 않고 기존 정상 snapshot 보존.
3. OWUI 성공 후 LiteLLM 실패 시 토큰 실패를 기록하고 독립적인 질문 분류는 진행. 전체 결과는 일부 실패.
4. 분류 중지/실패 시 완료한 결과는 유지. 다음 pending은 남은 것만 처리.
5. 브라우저 종료와 서버 프로세스 종료를 구분. 서버가 살아 있으면 작업 지속, 서버 종료 후 자동 재실행은 별도 설계하며 현재 있다고 주장하지 않음.
6. 모든 단계 완료 시 화면 조회 데이터를 갱신. 개요/사용자/토큰/카테고리 조회는 원천 API나 모델을 직접 호출하지 않음.

## 계획 API (미구현)

- POST `/api/dashboard/v2/operations/update?kind=quick|full`: 비동기 202와 runId.
- GET `/api/dashboard/v2/operations/status`: 현재 작업/단계/최근 실행 목록.
- GET `/api/dashboard/v2/operations/runs/{id}`: 단계별 진척과 안전한 오류.
- 분류 단계 중지는 기존 category stop과 연계. 수집 단계 전체의 즉시 중지 기능을 먼저 약속하지 않음.
- 대시보드 인증 동일. OWUI/LiteLLM 키는 백엔드 .env에만 보관. 에러나 상태 응답에 URL/원문/키를 넣지 않음.

실제 폐쇄망 검수에서는 연속 quick 2회 시 중복 증가 없음, 두번째 변경분 최소 반영, 단계별 실패/재시도/기존 데이터 유지, 초기 분류 후 신규 질문만 처리되는지를 확인합니다.
